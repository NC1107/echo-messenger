# 04 — Migration Plan

How to get from today's `GRP1:` half-wired state to the recommended `GRP2:` end state without breaking the small number of production groups already running with `is_encrypted=true`.

## Pre-requisites (do NOT start until these are done)

These are the audit's three P0 items (the third was upgraded after the security review re-graded skipped-key risk to HIGH). All three must be in production before any group E2E work begins; without them, group E2E will inherit the same message-loss surfaces.

1. **P0-1**: keyring-lock-failure surfacing (`crypto-audit/06-recommendations.md` → P0-1). Group decrypt failures will hit this exact code path with a much wider blast radius — every recipient of a group message hits it, not just one.
2. **P0-2**: OTP-heal retry + alarm (`crypto-audit/06-recommendations.md` → P0-2). Group rotation involves the same fire-and-forget upload pattern; same fix applies.
3. **P0-3** (was P1-1): "reset session" affordance for wedged 1:1 sessions (`crypto-audit/06-recommendations.md` → P1-1, now P0-3). The same UX pattern will be needed for groups when receivers can't decrypt at the active key version. Build the pattern once for 1:1, reuse for groups.

**These three can ship as a single bundled "loud-fail UX" PR (~400 LOC)**, per the security review's recommendation. They share an underlying state-machine pattern (typed exception → provider flag → banner → retry action) and splitting them creates three smaller PRs that all touch the same files.

**Phase 1 below is server-only**. It can land in parallel with the bundled client PR; they touch disjoint code paths and reviewing them independently is cheaper.

## Phase 1 — Server-side ciphertext-only enforcement (#591)

**Goal**: make it impossible for a buggy client to send plaintext into an `is_encrypted=true` group, AND make it possible for a correctly-encrypting client to send anything at all.

**Status**: ✅ Landed on `dev` ahead of this design doc. The earlier-existing `validate_encrypted_payload` had a bug: `is_valid_ciphertext_shape` only recognised 1:1 wire formats (initial V1/V2 magic byte + normal-message `header_len=40`). Group ciphertext arrives as `GRP1:<base64>` and `:` is not a valid base64 character, so the validator was silently dropping every encrypted-group send.

**What landed**:
- `is_valid_ciphertext_shape` now strips the `GRP1:` or `GRP2:` textual prefix BEFORE attempting base64 decode.
- Decoded payload must be ≥ 28 bytes (12-byte AES-GCM nonce + 16-byte tag floor).
- 7 new unit tests cover GRP1 accept, GRP2 accept, invalid base64 after prefix, payload too short, empty payload, case-sensitive prefix, and the regression itself.

**Shadow-mode discussion is moot** for this specific fix — the validator was rejecting all encrypted-group sends, not "letting plaintext through". The fix strictly *enables* a path that didn't work. There is no production client today that needs a soak window to migrate.

**Cost**: ~50 LOC + 7 tests, server-only. No client change. Already on `dev` in commit `<TBD>`.

A separate, future Phase 1.5 (still unbuilt) would extend the validator to also enforce that **the sender's user_id is currently a member** of the conversation (closes the "removed member tries to send" attack from `05-message-loss-analysis.md` L2). That's tracked in the audit P1-2 bucket, not here.

## Phase 2 — GRP2 wire format (client + server)

**Status**: Phase 2A ✅ (server schema + API for `min_wire_version`). Phase 2B ✅ (client-side static GRP2 packer/unpacker with Ed25519 sender signature). Phase 2C ⏳ (production wire-up: mint message_id client-side, plumb conv/msg context through WS frames, dispatch encrypt by cached `min_wire_version`).

**Goal**: support GRP2 alongside GRP1. Senders default to GRP2; receivers accept both — *within the bounds of the downgrade-attack mitigation below*.

- One PR. Adds the GRP2 packer/unpacker in `group_crypto_service.dart`. Adds Ed25519 sender signature.
- Server changes: a new column `group_key_envelopes.min_wire_version SMALLINT NOT NULL DEFAULT 1`. Set to `2` for any key version generated by a GRP2-capable rotator.
- All existing-version envelopes remain GRP1 (`min_wire_version=1`); new key versions are GRP2 (`min_wire_version=2`).

### Downgrade-attack mitigation

*(Added after the security review caught a real attack vector in the original "receivers accept both" draft.)*

Without a mitigation, a hostile member (or a compromised server, post-Phase-1) can frame ciphertext as GRP1 to bypass GRP2's sender signatures. The receiver sees `GRP1:` prefix → no signature verify → message accepted. The signature would be theatre.

**Mitigation**: receivers reject GRP1 wires when decrypting at a key version whose `min_wire_version >= 2`. Concretely:

1. Receiver parses the prefix → notes wire-version (1 or 2).
2. Receiver looks up `min_wire_version` for the envelope's key version.
3. If `wire_version < min_wire_version`: reject with `[Wire-version downgrade refused]` placeholder (different from both decrypt and signature placeholders).
4. Otherwise proceed with decrypt + (if v2) signature verify.

A genuinely-old client encrypting at an old key version still works because the old key version has `min_wire_version=1`. The mitigation only triggers when someone tries to send a GRP1-framed message *at a GRP2-only key version*, which is the attack we want to refuse.

Backward compat strategy:
- A receiver sees a GRP1 wire at a `min_wire_version=1` envelope → decrypts as today.
- A receiver sees a GRP2 wire at a `min_wire_version=2` envelope → verifies signature, then decrypts.
- A receiver sees a GRP1 wire at a `min_wire_version=2` envelope → **rejects**. This is the downgrade attempt.
- A sender that hasn't been updated yet emits GRP1; updated peers see the GRP1 wire is at a `min_wire_version=1` envelope (since the un-updated client doesn't trigger rotations) and consume it.

Estimate: 4–5 days code (was 3-4 — the `min_wire_version` column + receiver enforcement adds ~1 day), including tests and the cross-implementation wire-compat vectors (also closes P2-2 from the audit).

## Phase 3 — Deterministic leader election for rotation (#658)

**Goal**: rotation completes reliably with one online member.

- One PR. Adds the `leader = members[hash(...) mod N]` ordering + staggered backoff.
- Requires server to emit `trigger_event_id` on every membership-change / rotate-request event. Small server change.
- Tests: an integration test that simulates all-online, leader-only-online, follower-only-online, and split-brain (two leaders elected by inconsistent member views). The last one is the interesting case — we want to confirm the UNIQUE-constraint tie-breaker behaves as the spec says.

Estimate: 4–5 days.

## Phase 4 — Recovery UX

**Goal**: when group decrypt fails, the user can act.

- One PR. Frontend-only.
- Adds two banners:
  - *"You can't decrypt this group's recent messages. Fetch the latest key?"* (action: re-fetch active key version).
  - *"Sender signature failed."* (no automatic action; user contacts admin).
- Adds a developer-mode log of group-decrypt events for forensic capture.

Estimate: 3 days.

## Phase 5 — Toggle defaults

**Goal**: new groups default to `is_encrypted=true`.

- Smallest PR. One flag flip in the create-group screen + the server-side default.
- Rolled out behind a feature flag for two weeks. Monitor: rate of group-decrypt failures, rate of rotation-completion latency, rate of `[Could not decrypt…]` placeholders.
- If metrics stay clean, default flip ships.

Estimate: 1 day code + 2 weeks soak.

## Operational considerations (added after backend review)

These are operational concerns the backend specialist flagged that didn't fit cleanly into any single phase. Capturing them here so they aren't lost.

**Server-side enforcement location** (Phase 1): the right place for the structural validator is the send-path handler (`apps/server/src/routes/messages.rs:466`, adjacent to the existing `convo_meta.is_encrypted` branch), **not** a DB CHECK constraint. Cross-table predicates (`is_encrypted` lives on `conversations`, the content lives on `messages`) would require a trigger; the handler check is ~30 lines and easier to reason about.

**Search index waste** (Phase 1 follow-up): the GIN `to_tsvector('english', content)` index on `messages` still indexes ciphertext rows on insert even though query-time bypasses encrypted conversations. A partial-index migration (`WHERE NOT is_encrypted`) is a free perf win — land it as a separate small migration adjacent to Phase 1.

**Shadow-mode logs** (Phase 1): use structured `tracing` events with `encrypted_plaintext_violation=true` rather than a dedicated table. If log aggregation isn't wired (CLAUDE.md doesn't mention one), fall back to a tiny `encryption_violations` table with 30-day retention — 2 columns of index, low write rate.

**Shadow-mode duration** (Phase 1): the original "1 week then flip" was too calendar-driven. Replace with a *metric*: "zero violations from clients ≥ version X for 7 consecutive days". With low traffic on encrypted groups today, calendar-time alone doesn't yield enough evidence.

**Rate limiting** (Phase 3 + post-deploy): add per-user + per-conversation token-bucket on `POST /api/group-keys/:conversation_id/rotate`. Recommended: 1 rotation per 30 s per user per group. CLAUDE.md notes rate limiting is in-memory only — good enough for this; rotation is rare.

**Envelope-row growth**: `O(versions × members)`. A 200-member group at 12 rotations/year over 5 years is ~12 000 rows × ~200 B = 2.4 MB/group. Acceptable; no TTL needed. Stated here so future maintainers don't reinvent a GC scheme they don't need.

**Push notification UX** (resolves [`06-open-questions.md`](06-open-questions.md) OQ-6's option (b) — see that file for the final pick): option (b) "show sender + group name in push, content opaque" is explicitly **retired**. Leaking sender + group identity in the push payload is a metadata-leak privacy regression that runs counter to the project. The choice is between (a) generic *"new message in <group>"* and (c) silent push + client-side decrypt + locally-rendered preview. (c) requires background-decrypt on web/Linux, which doesn't exist; (a) ships everywhere today.

**Backup / disaster-recovery atomicity**: `group_key_envelopes`, `messages`, and `conversations.active_key_version` **must** be PITR-restored as a coherent snapshot. Restoring envelopes from an older backup than the live messages table leaves recipients permanently unable to decrypt messages whose key versions are missing. The 1:1 stack has the same property but the blast radius is one peer pair, not a whole group. Application code must never DELETE envelope rows — only `delete_group_dependents` on full conversation deletion, which already exists.

**Multi-device envelope keying**: open question for product review — see [`06-open-questions.md`](06-open-questions.md) OQ-10.

## Rollback plan

Each phase is independently reversible:

- Phase 1: revert the enforcement; logs continue.
- Phase 2: receivers continue to accept GRP1; senders fall back if a fresh `is_encrypted=true` group is created on an older client (we never *delete* GRP1 support).
- Phase 3: revert leader-election; falls back to "everyone races" — same behaviour as today.
- Phase 4: revert banners; users see the old `[Could not decrypt…]` placeholder.
- Phase 5: flip the default off; existing encrypted groups keep working.

There is no destructive irreversible step in the plan. **This is deliberate** and the design's response to the user's "I fear losing user messages" framing.

- Phase 1: 2 days code + 1 week soak.
- Phase 2: 4 days.

## What we are *not* committing to

- A date. The calendar above assumes nothing else lands; in reality, other features compete.
- Default-on for *existing* groups. Migration of plaintext groups to encrypted is a separate design problem — moving a multi-year message history through key versioning is not free. Out of scope here.
- MLS. We chose Sender Keys in [`02-protocol-options.md`](02-protocol-options.md). If product priorities later move toward 200+-member groups, we revisit then.
